CREATE TABLE users (
    user_id INTEGER PRIMARY KEY,
    name TEXT,
    username TEXT,
    exp INTEGER DEFAULT 0,
    monthly_exp INTEGER DEFAULT 0,
    plan_submitted INTEGER DEFAULT 0,
    last_active DATE DEFAULT CURRENT_DATE,
    agreed_to_tos INTEGER DEFAULT 0

CREATE TABLE tasks (
    task_id INTEGER PRIMARY KEY,
    chat_id INTEGER,
    bot_msg_id INTEGER,
    description TEXT,
    category TEXT DEFAULT 'Other',
    worker_id INTEGER DEFAULT NULL,
    reward INTEGER DEFAULT NULL,
    time INTEGER DEFAULT NULL,
    status TEXT DEFAULT 'open',
    start_time DATETIME,
    postponements_count INTEGER DEFAULT 0

CREATE TABLE quest_messages (
    message_id INTEGER PRIMARY KEY,
    task_id INTEGER,
    user_id INTEGER,
    user_name TEXT,
    message_text TEXT,
    is_reply_to_quest BOOLEAN DEFAULT 0,
    reply_to_message_id INTEGER,

    FOREIGN KEY (task_id) REFERENCES tasks(task_id)

CREATE TABLE exp_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER,
    exp_change INTEGER,
    change_date DATE DEFAULT CURRENT_DATE,

CREATE TABLE wiki (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    category TEXT DEFAULT 'Other',

    is_verified INTEGER DEFAULT 0,

CREATE TABLE task_metadata (

    contact_name TEXT,
    phone TEXT,
    address TEXT,

    priority_value INTEGER DEFAULT 0,

    scope_level INTEGER DEFAULT 0,

    FOREIGN KEY (task_id) REFERENCES tasks(task_id)

    proxy_url TEXT UNIQUE NOT NULL,

## 3. Описание проекта

### 3.1. Назначение и идея

**RPG AdminQuest** — корпоративный Telegram-бот с системой геймификации (RPG-квестов) для мониторинга и мотивации работы технической поддержки / IT-отдела.

**Основная концепция:** Каждый решённый инцидент (задача, тикет, заявка) становится "квестом". Исполнитель получает опыт (EXP), что повышает его RPG-уровень. Премия начисляется при достижении планового показателя за месяц.

### 3.2. Целевая аудитория

- **Пользователи:** Сотрудники IT-отдела / технической поддержки (7 человек в БД)
- **Администраторы:** Тимлид, управляющий квестами и проверяющий статьи Wiki
- **Менеджмент:** Директор компании, определяющий условия премирования
- **Внешние заявки:** Клиенты/сотрудники других отделов через веб-форму (web_quest.py, порт 5001)

### 3.3. Ключевые сценарии

1. **Получение квеста:** `/start` → просмотр квестов → принятие → выполнение → сдача с описанием
2. **Награда:** Автоматическое начисление EXP (5 за стандартный, 15 за критический инцидент)
3. **Wiki:** Просмотр базы знаний → использование статьи при сдаче квеста
4. **Дэшборд:** `/dashboard` — статус всех активных квестов
5. **Администрирование:** `/vacation`, `/smite`, `/reindex_now` (тимлид)
6. **Веб-заявки:** Внешняя HTML-форма (порт 5001) создаёт квест
7. **Телефония:** CallHandler (порт 5000) обрабатывает входящие звонки
8. **Автоанализ:** AI-анализ задач (определение компании, приоритета, категории)

### 3.4. Архитектура и техническая реализация

**Многопоточная архитектура:**
- `main.py` — основной цикл (asyncio) + Telegram polling
- Flask-сервер (порт 5001) — веб-форма заявок (отдельный поток)
- CallHandler (порт 5000) — телефония (отдельный поток)
- APScheduler — фоновые cron-задачи
- ProxyMonitor — мониторинг прокси-серверов
- `listen_to_calls()` — фоновая задача asyncio для очереди звонков

**Асинхронная БД:** aiosqlite (все запросы асинхронные)

### 3.5. Текущее состояние

**✅ Работает:**
- Полноценная RPG-система с EXP и уровнями
- Управление квестами (создание, назначение, выполнение, завершение)
- База знаний Wiki (79 статей, 9 категорий, верификация)
- Автоматическое начисление EXP

## 4. Сильные и слабые стороны

| Категория | Сильная сторона | Слабая сторона | Комментарий |
|-----------|----------------|----------------|-------------|
| **Архитектура** | Модульная структура (handlers/, services/, database/), асинхронная БД, отдельный поток для веб-сервисов | 17 сервисных файлов в одном каталоге, нет чёткой разграничения ответственности, Flask запускается inline через import | Архитектура рабочая, но сервисы смешивают логику (AI, wiki, прокси, звонки) |

## 📝 Резюме

### 5 главных выводов

1. **Проект работает и используется.** 1360 квестов, 84% completion rate, 7 активных пользователей, рост в 15.6 раз за 5.5 месяцев — это подтверждение product-market fit в нише корпоративной мотивации.

2. **Архитектура функциональная, но хрупкая.** Модульная структура (handlers/, services/, database/) — плюс, но 861-строчный `quests.py`, отсутствие миграций, и пустая таблица `companies` создают риски при масштабировании.

3. **Безопасность — критическая проблема.** Веб-форма без аутентификации, потенциально закоммиченный `.env` — это уязвимости, требующие немедленного исправления.

4. **Потенциал монетизации велик.** Формат "IT-поддержка в RPG" уникален для корпоративного рынка. Freemium модель с AI-аналитикой и интеграциями — реалистичный путь к доходу.

5. **Качество данных улучшаемое.** 52% квестов в категории "Other", 87 метаданных без компании, 0 записей в `quest_wiki_usage` — это зоны роста для AI-автоматизации.

### 3 первых шага

1. **Немедленно:** Добавить аутентификацию к веб-форме, убедиться что `.env` в `.gitignore`, включить `PRAGMA foreign_keys = ON` в БД
2. **В течение недели:** Разделить `quests.py` (861 строка) на модули, добавить градацию наград, запустить unit-тесты
3. **В течение месяца:** Внедрить FTS5 для Wiki-поиска, улучшить автокатегоризацию, добавить CI/CD
